## Tripmines were never in the game

You asked for tripmines in the Fix & Test-Tools wave. They were built: the
protocol constant, the sim logic, the hazard tags, the pattern that carries
them. And they never appeared in a single generated level.

`platform_kind_from_str` — the table that maps a catalog's platform kind names
to protocol constants — knew `CRUMBLE`, `JUMP_PAD`, `TRAMPOLINE`, the four
`RAMP_*` and `NORMAL`. It did not know `TRIPMINE`. So the strict catalog parser
rejected every pattern that used one, and `parse_catalog_lenient` — which exists
so one broken chunk cannot take the whole catalog down — removed those patterns
and carried on.

**127 of 132 chunks were loading.** Five were gone, silently, in every build.

The audit that should have caught it did not, because `8.hazard_entities` reads
the JSON dump rather than the loaded catalog. It reported
`hazard:tripmine: 1 patterns tagged, 1 carry a TRIPMINE platform (100.0%)` the
whole time. The tag was there. The pattern was not.

Fixed, plus four more chunks that were being dropped for their own reasons:

- `verify_socket` required a platform whose *top face* was at the socket's
  height. A ramp never has one — its walking height varies along the incline —
  so `ch05_ramp_of_embers`, a single ramp, was dropped. The check now accepts a
  ramp edge at any height inside the ramp.
- `ch05` then needed a landing deck: with the socket check fixed it loaded, and
  `5.ramp-anchors` failed, because its ramp top was only anchored if the
  neighbouring chunk happened to sit at exactly y=6.
- `pa_frost_fork` had 6 u sockets on 2.5 u arms, and the minimum legal socket
  width is 3.0 u — no legal socket existed. Arms widened to 3 u.
- `pa4_frost_fork` and `pa4_ruin_switchback` had 6 u sockets on 4 u arms.
- `pa_ember_fork` and `pb_mine_plaza` had sockets straddling a platform seam,
  so no single platform touched the edge across their width.

**135 of 135 chunks now load. Zero dropped.** A new test,
`every_shipped_chunk_parses_strictly`, asserts the strict parse succeeds, the
lenient parse removes nothing, and the count is pinned at 135. That is the alarm
that was missing.

## The playthrough bot now navigates

The playthrough kit is the only end-to-end test in the repo, and 4 of its 11
checks were permanently SKIP because the bot never completed a level.

The root cause was a harness bug, not a game bug. `wire.mjs` decoded `Snapshot`
only as far as `you` and stopped, with a comment saying callers that need more
must extend it. Nothing did. So `msg.gifts_taken` was always `undefined`, the
bot's collected set never grew, and it walked back to the gift it had just
picked up — forever. The server was collecting gifts correctly the whole time.

Four more defects in the bot itself:

- `this.pos` was the bare `Vec3`; `grounded` lives on `ControllerState`.
  `Boolean(undefined)` is `false`, so the jump button was never pressed.
- A straight-line steer walked off the platform. The server logged
  `player out; spectating cause=0` (`DEATH_VOID`) for every client. The bot now
  probes one step ahead against the platform AABBs and either jumps at a
  landing inside jump range or gives up on that gift.
- Greedy nearest-target selection oscillated — the velocity trace reversed sign
  every second. Hysteresis holds the current target until it is collected,
  blacklisted, or something is 4x closer.
- `len > 2.0` made the bot jump whenever the gift was more than 2 u away, which
  is always, and a bot that jumps every frame never builds horizontal speed.

**39 of 88 gifts collected in 60 s, was 0.** `draft` is a live check now — it
fires before level 1, so it never needed a completed level. Playthrough went
from **7 pass / 3 skip / 1 fail** to **8 pass / 2 skip / 1 fail**.
