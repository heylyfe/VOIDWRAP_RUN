## T-155 — the vote pool gets its own dump, in the crate that owns it

Cycle 23 ended with two `6.enemy-frequencies.*` metrics SKIP because the pattern audit could not
see the vote pool. The owner closed the crate-move route ("a debug utility never justifies
architecture churn") and pointed at the additive one: record the offered pool per level in the
dump record.

`voidwrap-server --dump-pool` prints one NDJSON record per (mode, level) — 120 records — and exits
before `startup()`. Each record carries the fresh pool plus a `gated` list: enemies held back only
by a `requires` hook, with the requirement and a `satisfiable` flag computed where the tag data
lives. Without that, `chorus` (2x `small` permanents) would read as dead registry content.

The audit joins the two dumps by (mode, level):

- `6.enemy-frequencies.never-offered` — every roster enemy must appear in some pool, or be gated
  with a satisfiable requirement. An unsatisfiable gate FAILs.
- `6.enemy-frequencies.pool-depth` **replaces** `always-offered`, which asked whether a type
  appeared in 100% of a cell's levels — true by construction for a pool, so it could only fire on
  a non-defect. A vote needs 3 options.

Both SKIP without a pool table and FAIL on an empty one. The selftest plants four defects and
proves the gate path both ways.

**Pattern audit: 17 lines, 0 failed, 2 skipped -> 17 lines, 0 failed, 0 skipped.** Pool depth
3-19; all 20 registry enemies reachable.

## T-156 — the bot walks: two real bugs, level completion still parked

The bot had been blamed for two cycles on "a greedy straight-line steer cannot clear a gap it
cannot probe". That was not the bug. Two measurement bugs were, and both were invisible from
outside because the symptom was always the same: the bot fell off the map.

1. **The bot fed the server 80 input frames per second.** `startWalking` sent 4 frames every
   50 ms; the server drains `PHYSICS_HZ / TICK_HZ = 60 / 20 = 3` frames per tick = 60 frames/s.
   The queue filled to `MAX_QUEUED_INPUTS` and dropped the excess, so **every input was applied
   about a second late**. That is why the bot could see an edge, press jump, and still fall.
2. **The bot had no horizontal control in the air.** `nearestLanding` returns the point directly
   below an airborne bot, so `aimX/aimZ` became the bot's own position and `dirX/dirZ` became
   `(0,0)`. Measured: **2715 of 3431 steer frames (79%) degenerate, every one airborne.** After
   the fix: **0 degenerate frames in 818.**

Also fixed: the edge probe measures edge distance in 0.15 u steps and only accepts a landing
inside `jumpReach(rise)`; the `rise > 0.3` bunny-hop heuristic is gone; `safeToJump` gates the
unstick jump on ground continuing for the full jump reach; `nearestOn` insets 1 u so the route aim
is never the bot's own position.

New `VOIDWRAP_SEED` (dev/QA aid, warns on startup) — every run used a clock seed, so no two
playthrough runs were comparable, which is how the input-rate bug survived several "it got
better" readings that were really just easier levels. New `--trace <path>` writes per-steer NDJSON.

**Fixed seed 7, 240 s, one client:** before 22/46 gifts (47.8%) + 1 void death at tick 750; after
**25/46 (54.3%), 0 deaths, full 240 s**. 8-client sweep seed 7, 90 s: **43/88 (48.9%)**, up from
30.7%. This cycle's sweep reads **51/88 (58.0%)** — the bot's steering is wall-clock driven, so
the number moves a little run to run.

**Still parked:** the bot cannot empty a level. The remaining blocker is **vertical routing** — a
gift directly above or below the bot has no route, so the bot blacklists it and holds. Two
shortcuts both measured worse and were reverted (jump when degenerate: 14/46 + a death; blacklist
when degenerate: 9/46). New `level-completion` check: SKIP with the number and reason, a live PASS
the moment a level is emptied by walking. Deliberately not a FAIL — a permanently red line trains
the gate to be ignored.

### The client side, and the first cut that was wrong

The obvious approach — clone the glTF scene per instance and hand it to `<primitive object>` — is
wrong twice over. `MODEL_COMPONENTS` mounts 24 slots of every model and one `Object3D` cannot have
two parents, so 23 of the 24 slots would render nothing; and a shared material cannot animate
`emissiveIntensity` per enemy, so two visible Coils could not wind independently.

Cloning and detaching the materials fixed both, and then the React Compiler lint
(`react-hooks/immutability`) rejected mutating a `useMemo` value inside `useFrame` — correctly.
The other 18 models all keep their mutable three.js objects in refs.

So the shipped version is declarative, matching the rest of the roster: each glTF node's
*geometry* is reused (shared across all 24 slots, cheaper than cloning) and its *translation* is
read off the node at render time, while the material is a per-instance JSX
`<meshStandardMaterial>` and the animation drives refs. The Blender script stays the single source
of truth for both shape and placement.

The accent is no longer a literal in the `.tsx`; `enemyLookForBehavior()` reads `ENEMY_LOOKS`, so
the palette table stays the single source of truth for emissive trim — the thing T-145's
uniqueness test guards.
