# T-130 — Death instrumentation: the bots were falling, not being killed

**Cycle:** 13 · **Agent:** orchestrator · **Status:** PASS

## Why

The playthrough kit has reported `FAIL - level-progression` since T-115, and
`vote` / `shop` have been `SKIP` because the bots never reach a second level. The
blocker was never code — it was a **missing measurement**: the harness could see
that its bots died, but not *where* or *why*. The snapshot carries position, not
cause, and the server's `tracing` output is not machine-readable.

T-124 tried to fix this from the bot side (a platform-graph BFS) and was parked for
"no measured win" — it was optimising a bot whose failure mode nobody had named.

## Change

1. **`server/crates/server/src/deathlog.rs`** — an optional NDJSON death log, off
   unless `VOIDWRAP_DEATH_LOG` names a path. One line per death:

   ```json
   {"tick":235,"level":1,"player":5,"cause":0,"x":0.800,"y":-16.810,"z":-2.980,
    "vx":-5.530,"vy":-32.530,"vz":-7.090,"kill_y":-16.000,"lives":0,"out":true,"note":"void"}
   ```

   `init()` opens the file at startup so a harness can tell "log on, no deaths"
   from "log never on". A write failure is logged once and ignored — a diagnostic
   must never take the tick loop down.

2. **`tools/playthrough/run.mjs`** — `--death-log <path>` (or
   `PLAYTHROUGH_DEATH_LOG`) prints a `death-log` line on every run:

   ```
   PASS - death-log (8 deaths (void:8), 8 ended a run, deepest fall y=-17.36; levels: 1)
   ```

   Informational, not a gate: a death is not a failure. The point is that the cause
   split is now printed instead of invisible.

3. **`tools/verify-live.mjs`** — starts the server with `VOIDWRAP_DEATH_LOG` pointing
   at a temp file and passes it to the playthrough, so the gate reports death causes
   on every run.

## The finding

First run with the log on, 8 clients, 60 s:

```
deaths: 8
by note/out: {('void', True): 8}
```

**Every death is a fall, and every one ended the run.** Not one enemy kill. The
bots are not being killed by the game — they walk off the map.

The second half of that is the interesting part: `out: true` on all eight means
`run.lives == 0` at the moment of death. `Run::new` initialises `lives: 0`, and the
only way to get a spare life is the rare `spare_wick` upgrade (+1 life). So **the
first fall of a run is always fatal**, for every player, at every level.

That is a balance decision, not a bug, and the owner deferred balance. It is
recorded as the top tuning note below rather than changed.

## Evidence

| | before | after |
|---|---|---|
| death cause visible to the harness | no | **yes** |
| `death-log` line in the gate output | absent | **`8 deaths (void:8), 8 ended a run`** |
| server tests | 150 | **151** |
| `just verify-live --port 7979` | PASS 5/5 | **PASS 5/5** (playthrough now 8 pass / 3 skip) |

## Tuning notes — for the owner's balancing pass

1. **Starting lives = 0.** Measured: 8 of 8 deaths ended a run. A single missed jump
   ends a player's run on level 1. For 8-player co-op on a platformer with fall
   hazards this is the harshest knob in the game. Candidates: start at 1 life, or
   make `spare_wick` `common` instead of `rare`, or grant a life per level cleared.
   Do not change without measuring the death rate first — the log now makes that
   measurable.
2. **`kill_y` is 15 u below the lowest platform.** The bots fall 15 u before dying,
   which is ~0.9 s of falling. If falls should feel more forgiving, a shorter drop
   is the knob, not the death rule.
3. **The bots still fall.** That is T-124's parked problem and it is a *bot* problem:
   the game is not killing them unfairly. The next attempt at the bot should use the
   death log to check whether it is falling at edges (no ground probe) or at seams
   (probe says ground, collision disagrees) — the two have different fixes.

## Choice log

- **Side-channel file, not a snapshot field.** Adding `cause` to the snapshot would
  have meant `just gen` + `just fixtures` and a protocol version bump for a
  diagnostic that no client reads.
- **Informational check, not a gate.** Making "0 deaths" a pass condition would fail
  the gate whenever the bots got worse at the game, which is not what the gate is
  for. The line exists to be read.
- **Did not change starting lives.** The owner's directive is explicit: balancing
  comes after, ship functional-not-tuned, write tuning notes instead of grinding
  balance. Changing the harshest knob in the game on the same night as measuring it
  would be exactly the wrong order.
