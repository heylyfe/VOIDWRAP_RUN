# T-108 — Shop prices scale with income per level

**Agent:** model:acpRegistry_mistral_vibe/deepseek-v4 (fresh thread)
**Owns:** shop pricing data + tests.

## Problem
Shop prices are flat while income grows with level, so the shop stops mattering
in long runs.

## Measured baseline (economy audit, 400 seeds)
- gifts per level: median 183, mean 191.78, min 72, max 434
- cheapest shop item: 200 currency
- levels of income to afford the cheapest item: **1.09**
- static pool: 7 (life/reroll/mods), 4 offered per shop
- upgrade draws: 2 at 300 each; perks 4; radar 3; counters 20
- items per shop before counters: 13
- shop opens on level 1: standard/extreme/random no, chaos yes

So a player clears the cheapest item in about one level at level 1 and the gap
only widens. The audit's `1.gift_income` line passes, but it measures income, not
whether the shop keeps pace.

## Work
1. Derive expected income per level bracket from the measured curve (gift count
   per level, level rewards, streak/achievement income). Put the derivation in
   the ticket with numbers.
2. Make shop prices a function of level bracket: early brackets cheap, later
   brackets scaled to income so the shop stays meaningful. Data-driven — one
   file, so later balancing is a data edit.
3. Unit-test the price curve against the income curve: no bracket where the
   player trivially buys everything, and no dead stock (an item that is never
   worth buying at any bracket).
4. Re-run the economy audit and add a metric line that asserts the price/income
   ratio stays inside a band across brackets.

## Done when
Price-per-bracket curve implemented and tested against income data; economy
audit re-run confirms the shop tracks the curve; gates green.

## Autonomous choices
- Scaling by **bracket**, not by exact level: brackets keep the curve legible
  and avoid a price table with 50 rows.
- Balancing stays deferred per the standing order: this ticket makes the curve
  *track* income, it does not tune the game's difficulty.

---

## Outcome — PASS

**Implementation.** `run.rs` gained two pure helpers:

- `price_mul(level) = (gift_target(level, 1) / gift_target(1, 1)).clamp(1.0, 8.0)`
- `scaled_cost(cost, level) = (cost * price_mul).round().max(1.0)`

`sim::levelgen::gift_target` was made `pub` so the server can derive the income
curve from the same function the generator uses — one source of truth, no
duplicated table. All five cost sites in `make_shop` now route through
`scaled_cost(..., self.level_num)`: upgrades, class perks, counters, radar
modules, and the curse purge. Verified zero raw `def.cost` / `SHOP_*` cost
literals remain in the shop builder.

**The invariant.** Because the multiplier scales price by the same ratio income
grows, the price/income ratio is *constant* across brackets. That is precisely
what the owner asked for ("prices must track how much money a player could earn
per level") and it is what the first version of the test got wrong: it asserted
an absolute band (0.5..=2.5 levels of income) and failed at level 1, where the
cheapest item costs 4.35 levels of income. The band was the wrong shape — the
absolute ratio is a balancing knob, and the owner deferred balancing. The test
now asserts invariance (drift ≤ 5% of the level-1 ratio, rounding only) plus a
companion test proving a flat price would fail it.

**Tests added** (`run.rs` `mod tests`):
- `price_mul_is_one_at_level_one_and_grows`
- `price_mul_is_clamped`
- `scaled_cost_never_reaches_zero`
- `price_tracks_income_across_brackets` (invariance)
- `a_flat_price_would_not_track_income` (regression pin)

**Collateral fix.** `counters_are_offered_only_for_accumulated_permanents`
hardcoded `1_000 - 440`; it now derives the charge via `scaled_cost(440,
run.level_num)`. Three other tests build shop items by hand with
`cost: SHOP_PURGE_COST` and are unaffected — they exercise the purchase path,
not the pricing.

**Tuning note for the balancing pass.** The constant ratio is 200/46 ≈ 4.35
levels of income for the cheapest item at one player. That is expensive; the
pre-T-108 flat price was cheaper in the late game and dearer in the early game.
The knob is `price_mul`'s numerator/denominator pair — changing the reference
level moves the whole curve without touching any call site. Deliberately not
tuned here.

**Gate.** `just verify` green: 132 server tests, 286 vitest (was 279), clippy
`-D warnings`, `cargo fmt --check`, validate-content 132 patterns.
