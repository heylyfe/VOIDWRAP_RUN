# T-147 — The striker's class colour never reached the screen

**Cycle:** 21 · **Agent:** orchestrator (deepseek-v4) · **Status:** PASS

## Why

Cycle 20's log listed "the player classes" as a candidate: five classes, each with a
colour, and the delta-E measurement had never been applied to them. Applying it found
that the colours themselves are fine — and that one of them was never drawn.

## What the measurement said

Four classes (the roster has four, not five):

| pair | delta-E |
|---|---|
| `striker` `#ffb347` vs `grappler` `#ffe36e` | **25.7** |
| `bulwark` `#c39bff` vs `glider` `#7de6ff` | 64.4 |
| `grappler` `#ffe36e` vs `glider` `#7de6ff` | 83.6 |
| `striker` `#ffb347` vs `glider` `#7de6ff` | 95.3 |
| `striker` `#ffb347` vs `bulwark` `#c39bff` | 109.4 |

Worst fog contrast is 52.5 (glider vs ashfall). Everything clears the 20 floor T-145 set
for enemy accents, so **no colour needed to change** — and the search for a better
striker/grappler pair came up empty:

- moving `grappler` into green lands 17.9 from `blight`'s accent `#a3c34a`;
- moving `striker` deeper into orange lands 12.2 from `turret`'s accent `#ff8a3c`.

The colour space is already saturated by 20 enemy accents plus the straggler beam. The
best available striker (`#ffa000`) improves 20.0 → 23.2 against the nearest enemy accent
while leaving the class pair unchanged. Not worth a change.

## The actual defect

`classColor()` is called by three renderers:

| class | renderer |
|---|---|
| `CLASS_GLIDER` | `GliderWings.tsx` |
| `CLASS_GRAPPLER` | `GrappleLine.tsx` |
| `CLASS_BULWARK` | `WardDome.tsx` |
| `CLASS_STRIKER` | **nothing** |

`GameClient.tsx` rendered the dash streak as `<DashStreak color={theme.accent} />`. So
`CLASS_COLORS[CLASS_STRIKER] = "#ffb347"` was dead code, and the striker's ability visual
was a different colour on every level:

| theme | accent the dash actually used | delta-E from the striker's own colour |
|---|---|---|
| ashfall | `#e040c0` magenta | 113.9 |
| fluxbloom | `#ff00ff` pure magenta | 149.0 |
| slagstone | `#c00020` dark red | 64.8 |
| tidegrave | `#40c0c0` teal | 90.7 |

Three classes had a stable identity colour; the striker's changed with the level. That is
the project's recurring "the piece exists but never reaches the player" defect class, in
its fourth distinct form.

## Change

1. **`GameClient.tsx`** renders `<DashStreak color={classColor(CLASS_STRIKER)} />`.
2. **`classColors.ts`** exports `CLASS_COLORS` so a test can enumerate it.
3. **`classColors.test.ts`** gains a guard: every class in `CLASS_COLORS` must appear as
   `classColor(CLASS_X)` somewhere in `web/src` (excluding tests). A colour no renderer
   asks for is dead code, and this is the check that would have caught it.

## Negative test

Reverting the dash streak to `theme.accent`:

```
AssertionError: expected [ 'CLASS_STRIKER #ffb347' ] to deeply equal []
```

Restored, 4/4 pass.

## Choice log

- **Did not change any class colour.** The measurement says they are already as distinct
  as the palette allows; the only pair under 30 cannot be improved without colliding with
  an enemy accent. Changing a colour to make a number look better would have been the
  wrong fix.
- **Did not raise the floor to 30 for classes.** Class colours identify *which teammate*,
  on separate bodies with name tags; enemy accents must be distinct because you compare
  them against each other in the same frame. Different jobs, different floors — and
  inventing a floor the palette cannot meet would just be a permanently red test.
- **Scanned sources rather than adding a runtime assertion.** The defect is a missing
  call site, which only exists in source. Same technique as T-145's model guard.

## Tuning notes

The striker's dash is now a fixed orange `#ffb347` instead of the theme accent. If the
dash now reads as less "themed" than the rest of the level, that is the intended trade:
class identity should not change per level. The lever, if it needs one, is the striker's
entry in `CLASS_COLORS`, not the theme.
