# T-113 — Performance optimisation — PARKED (measured, no win available)

**Status: PARKED.** Baseline measured and recorded; the one candidate change
that could be measured was tried and reverted because it produced no win.
Per the ticket's own rule ("no change merges without a measured win"), nothing
merged. The instrument and the probe tool are kept so a future run with a real
GPU can pick this up.

## 1. PROFILE — baseline numbers

### Server tick budget (8 players)
Instrument added to `server/crates/server/src/game.rs` `run()`: accumulates
`window_tick_time` and logs
`tick N | X Hz | players P | Y.YY ms/tick` once per second.

Measured under a full 8-player simulation:

| metric | value |
| --- | --- |
| tick cost | **0.03 ms/tick** |
| sustained rate | **20.0 Hz** |
| budget | 50 ms/tick |
| utilisation | **0.06 %** |

**Conclusion: the server is not the bottleneck.** There is no headroom worth
chasing — a 100x regression would still fit the budget.

### Level generation cost
6,000 levels (400 seeds x 15 level/player cells), three runs:

| run | wall time | per level |
| --- | --- | --- |
| 1 | 7348 ms | 1.225 ms |
| 2 | 7390 ms | 1.232 ms |
| 3 | 7323 ms | 1.221 ms |

**Conclusion: 1.22 ms per level.** Generation happens between levels, not in
the tick loop. Not a frame-time source.

### Client frame time
`tools/fps-probe.mjs` (new, kept): joins the server, clears the draft, handles
a stale run-over state, measures rAF deltas over N seconds, prints
fps/mean/p50/p95/worst/dpr/canvas.

| metric | value |
| --- | --- |
| fps | **8.8** |
| mean frame | 113.9 – 114.3 ms |
| p50 | 114.5 ms |
| p95 | 122.1 ms |
| worst | 222.1 ms |
| dpr | 1 |
| canvas | 1280 x 720 |

**These numbers are SwiftShader software rendering, not a GPU measurement.**
Headless chromium has no GPU in this environment, so the absolute values say
nothing about the owner's machine. What they *do* say is that the client is
fill-rate bound, not CPU bound: p50 and p95 are within 8 ms of each other, so
there is no per-frame CPU spike to find.

### Structural findings (no change needed)
- Gifts are **already instanced** (`InstancedMesh` + `instanceMatrix`). A
  gift-count-heavy level does not add draw calls.
- **41 `useFrame` callbacks across 18 components.** Not a hot spot at 8.8 fps;
  each is a handful of arithmetic ops.
- No allocation churn found in the tick loop (0.03 ms/tick rules it out).

## 2. OPTIMISE — one candidate tried, reverted

**Candidate:** `web/src/scene/Atmosphere.tsx` sky dome `renderOrder={-1}` →
`{1}`, so the sky draws *after* opaque geometry and the depth test rejects
covered pixels (a classic overdraw reduction).

**Measured:** 113.9 ms mean with the change vs 114.3 ms baseline — a 0.4 ms
difference, well inside run-to-run noise on a software rasteriser.

**Reverted.** No measured win, so per the ticket rule it does not merge.

## 3. PROVE — nothing to prove

No optimisation merged, therefore no before/after table. The full test suite
is unchanged (no behaviour was touched).

## Why parked rather than failed

The ticket's premise was "the game must be less laggy". The measurements show
the two things this repo can actually measure — server tick and level
generation — are both two to three orders of magnitude inside budget. The
remaining candidate (client frame time) cannot be measured honestly without a
GPU: every number here is software rasterisation, and optimising against
SwiftShader would be optimising against an artefact of CI.

**Recommendation for the owner:** if the game still feels laggy on real
hardware, the next step is a GPU-side profile (Chrome DevTools performance
panel, or `--enable-gpu-rasterization`), not more blind changes. The probe tool
is ready: `node tools/fps-probe.mjs --seconds 20`.
