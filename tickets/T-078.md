# Ticket T-078: pedestal voting core (server + protocol)

Server-authoritative voting over the existing WebSocket layer. This replaces the automatic "one enemy
per level" scaling with a vote that happens EVERY level, per the owner's explicit request.

## What exists (verified)

- `protocol/schema.json` defines `ClientMsg` (`Hello`, `Inputs`, `Ping`, `Restart`, `DraftPick`,
  `Buy`, `ChooseClass`) and `ServerMsg` (`Welcome`, `Level`, `Snapshot`, `Pong`, `Error`, `RunOver`,
  ...). Generated code is never hand-edited: change the schema, then the lead runs `just gen` and
  `just fixtures`.
- `server/crates/server/src/game.rs` owns the tick loop and the run flow: lobby with a draft offer ->
  vote -> generated level -> collect -> golden gifts + beacon -> lobby.
- `server/crates/server/src/run.rs` owns `Run` (level number, phase, mods, currency) and the shop.
- `design/ENEMY_REGISTRY.md` (from T-072) defines the pool rules: `min_level`, `selection_cap`, tags,
  class interactions, and the overflow rule when every cap is exhausted.
- `design/content.json` holds the enemy registry entries.

## The voting system

- A vote session opens at level 1 and at EVERY level, during the collapse/exit window (after the
  normal gifts are collected, while players head for the beacon).
- Three options are drawn from the enemy registry pool, filtered by: `min_level <= current level`,
  `selection_cap` not yet reached by the run's permanents, and class interactions (an enemy that
  refuses to spawn against a class present in the lobby is not offered).
- Curse options use the same system and the same session: one of the three options may be a curse
  instead of an enemy, drawn from the existing curse content.
- All connected players vote. 20 s countdown. Majority wins. A tie goes to the host's vote; if the host
  did not vote, the server flips a coin deterministically from the run seed and the level.
- The winner becomes PERMANENT for the rest of the run: it is added to the run's permanent list and
  spawns on every subsequent level.
- Overflow: when every registry entry has reached its cap, the options summon TEMPORARY enemies for
  the next level instead of adding a permanent.
- Votes survive reconnects: a player's vote is keyed by player id, not by connection.
- The previous automatic scaling (one enemy per level, capped) is REMOVED and replaced by this system.

## Protocol

Add what the client needs, minimally: a `VoteOpen` server message (options with ids, names, kinds,
countdown), a `VoteState` (per-option counts, who has voted, seconds left), a `VoteResult` (winner,
new permanent), and a `Vote` client message (option index). Keep every existing message working. Note
in NOTES that the lead must run `just gen` and `just fixtures`.

## Requirements

- Unit tests: majority, tie to host, tie with no host vote, cap-aware pool building, pool scaling by
  level, permanence across levels, overflow to temporary, rejoin preserving a vote, and the countdown
  closing the session.
- Deterministic: the coin flip and the option draw come from the run seed and level, never from the
  clock.
- Doc-comment every public item. No `unwrap` outside tests.

## Output format

Complete files with `=== FILE: <path> ===` ... `=== END FILE ===`, or single functions with
`=== FN: <path> :: <name> ===` ... `=== END FN ===`. Allowed paths: `protocol/schema.json`,
`server/crates/server/src/`, `server/crates/sim/src/` (only if a shared type is genuinely needed).

Do not touch `web/` or `design/`. No new dependencies.

## Done when

`cargo test -p server` passes with the new tests, `cargo clippy --workspace --all-targets -- -D
warnings` is clean, and the protocol additions are described precisely enough for the lead to run
`just gen` and `just fixtures` without guessing.
