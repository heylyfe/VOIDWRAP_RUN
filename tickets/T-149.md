# T-149 — the pedestal vote had a complete client UI that nothing mounted

**Cycle:** 21
**Status:** PASS
**Area:** `web/src/game/{session,store,GameClient}.tsx`, `web/src/hud/vote/protocolAdapter.ts`

## What was wrong

The server opens a vote session every level, at the moment the level enters
`LEVEL_COLLAPSE_PENDING` (`game.rs:939` → `open_vote_session`). It broadcasts `VoteOpen`,
then `VoteState` on every ballot, then `VoteResult`. It accepts `ClientMsg::Vote { option }`
and closes the session early once every joined player holds a ballot.

The client had all of it:

| piece | state |
|---|---|
| `hud/vote/VoteWidget.tsx` | renders the three pedestals |
| `hud/vote/useVote.ts` | reducer + send callback |
| `hud/vote/protocolAdapter.ts` | parses the three wire messages |
| `hud/RunVoteOverlay.tsx` | the in-run overlay, built for exactly this |
| `hud/LobbyPoll.tsx` | the lobby variant |

Every one of them had tests. **None of them was mounted.** `LobbyPoll` and
`RunVoteOverlay` were imported by nothing outside their own test files, `GameClient` never
read a vote message, and `session.ts` had no method that could send a ballot — its send
surface was `DraftPick`, `Debug`, `Buy`, `ChooseClass`, `Restart`, `Inputs`, and nothing
else.

So the vote ran every level, invisibly, and `VoteSession::resolve` fell through to its
last resort:

```rust
let winner = if tied.len() == 1 { tied[0] } else {
    match self.host.and_then(|h| self.ballots.get(&h).copied()).map(usize::from) {
        Some(ballot) if tied.contains(&ballot) => ballot,
        _ => { let mut rng = Rng::new(...); tied[rng.below(tied.len())] }   // <- always this
    }
};
```

With zero ballots every count is 0, every option ties, the host has no ballot, and the RNG
picks. **Players gained a random permanent every level and were never shown the choice.**

This is the project's recurring "the piece exists but never reaches the player" defect in
its purest form: not a missing feature, a missing wire.

## The fix

1. **`store.ts`** — `voteMessages: unknown[]`, a capped log of the three vote messages.
2. **`session.ts`** — `case "VoteOpen" / "VoteState" / "VoteResult"` append to that log
   (last 64), and a `vote(option: number)` method that sends `{ type: "Vote", option }`.
3. **`GameClient.tsx`** — mounts `<RunVoteOverlay messages={voteMessages} onVote={...} />`
   next to the tester panel. The overlay returns `null` outside a vote, so nothing changes
   for a player who is not voting.
4. **`protocolAdapter.ts`** — the adapter was written against *assumed* field names while
   T-078 was in flight, and its own header said so. The real protocol sends `countdownS`
   and `secondsLeft` (whole seconds), not `durationMs` / `remainingMs`, so the countdown
   would have shown the local 20 s default instead of the server's. Both spellings are now
   accepted, and the header records the real shapes.

## Evidence

**The chain, end to end, from a real frame.** `vote.test.ts` feeds a `VoteOpen` in the
exact shape `protocol/generated.ts` produces through `parseVoteMessage` → `voteReducer` →
`VoteWidget` and asserts the rendered markup contains all three pedestal names, that the
vote reads as open, and that the countdown is 20 s.

**The wire, pinned.** Four tests cover `countdownS` (including a non-default 7 s, so a
silent fallback to the local default cannot pass), `secondsLeft`, and `VoteResult.winner`.

**The wiring, guarded.** `voteWiring.test.ts` reads the source, because the defect is a
missing wire and no runtime assertion can see a component that was never rendered. It
asserts the overlay is imported and mounted with both `messages` and `onVote`, that the
store selector feeds it, that all three message types are handled, that `vote()` exists and
sends the right frame, and that the store declares the log.

**Negative test.** Removing the `<RunVoteOverlay … />` line fails the guard with
`expected '"use client";\n\nimport { Canvas, use…' to match /<RunVoteOverlay\b/`. Restored,
5/5 pass.

**No rendering regression.** `tools/capture.mjs` drove the full flow against a live server
(title → lobby → spawn → moving → stopped → falling → run summary → new-run lobby) with
**zero page errors and zero console errors**. Its only failure was the headless tick-rate
floor (12/s), which the tool itself reports as a software-rendering artifact.

## Choice log

- **Mounted the existing overlay rather than writing a new one.** `RunVoteOverlay` was
  already designed for the in-run collapse window, already tested, and already anchored so
  it does not occlude the beacon. Writing a second one would have been a redesign.
- **A message log in the store, not a vote-specific state machine.** `RunVoteOverlay` takes
  `messages: readonly unknown[]` and replays them through `useVote`; feeding it the raw
  frames keeps the reducer as the single source of vote state and means the overlay needs
  no changes at all.
- **Capped at 64 messages.** A long run opens a session per level; the log must not grow
  without bound. 64 covers several levels of open/state/result traffic.
- **Fixed the adapter instead of the protocol.** The adapter's header says it is "the ONLY
  module that knows the wire shape" and that it absorbs protocol differences. That is
  exactly what was needed; changing the protocol would have been a `just gen` + `just
  fixtures` change for a client-side naming mismatch.
- **Left `LobbyPoll` unmounted.** It is the lobby variant and the lobby already has
  `DraftScreen` for card picks. Mounting both would put two vote surfaces on screen. It
  stays as dead code with a note; deleting it is a separate decision.
- **Did not add a debug command to force the collapse.** It would have made a browser E2E
  possible, but `design/DEBUG_COMMANDS.md` is a frozen contract and this ticket does not
  need it — the unit chain proves the same thing.
