# Ticket T-069: pattern format + composition engine (STAGE 1)

This is the foundation of the owner's biggest request: 50-100 patterns composed so that every level
feels unique. You write the FROZEN SPEC and the engine that consumes it. You do NOT author patterns
(T-070/T-071 do that against your spec).

## What exists (verified)

- `design/chunks.json` holds 25 chunks. A chunk is a data level fragment: `id`, `name`, `role`
  (hub/path/junction/dead_end), `min_level`, `difficulty` (1..3), `tags`, `platforms`, `sockets`
  (entry/exit anchors with a facing and a width), `gift_slots`, `enemy_slots`, `altar_slots`, `beacon`.
- `design/CHUNK_FORMAT.md` is the binding spec for that file.
- `server/crates/sim/src/levelgen.rs` assembles a level: a hub at the origin, then a budget-driven
  random walk over open sockets. Each step picks an open socket at random, then `try_place` samples
  candidate chunks, rotates them by a multiple of 90 degrees, and accepts the first that stitches
  (socket alignment, no overlap, stacking clearance). `chunk_weight` biases by difficulty tier and by
  the level's event. `validate` then checks reachability over the platform graph.
- The generator is deterministic: `generate_for_with_spacing(seed, level, players, spacing_mul)`.
  Same seed and level must always produce the same level.

## Part 1 - the frozen pattern spec (`design/PATTERN_FORMAT.md`, new file)

Write the binding spec for a PATTERN. A pattern is the same data fragment as a chunk, extended so the
composition engine can reason about it. It must cover, at minimum:

- Identity: `id`, `name`, `role`, `min_level`, `difficulty`.
- **Theme tags** (what the place looks like and feels like): a closed vocabulary you define, e.g.
  `ember`, `void`, `frost`, `ruin`, `garden`, `machine`, `spire`, `hollow`. List every allowed value.
- **Mechanic tags** (what the player does there): a closed vocabulary, e.g. `climb`, `drop`, `span`,
  `bounce`, `crawl`, `gauntlet`, `rest`, `loot`, `fork`, `dead_end`. List every allowed value.
- **Hazard tags** (reserved for later waves): `trampoline`, `tripmine`, `fog`, `crumble`. Patterns may
  declare them; nothing consumes them yet.
- Entry/exit anchors: the existing `sockets` (id, pos, facing, width), with the rule that a pattern
  must have at least one socket and that socket widths are compatible with the chunk rules.
- Spawn points: `gift_slots`, `enemy_slots`, `altar_slots`, `beacon` exactly as today.
- Composition constraints the engine must honour: which roles may follow which, minimum and maximum
  run lengths, and how tags interact (e.g. two `rest` patterns may not be adjacent).
- A worked example pattern in full JSON.

State explicitly that this spec SUPERSEDES `design/CHUNK_FORMAT.md` for new content, and that the
existing 25 chunks are valid patterns once they gain the new tag fields.

## Part 1b - the catalog is split across files (frozen)

Two agents will author patterns in parallel and must never touch the same file. Make the loader read
THREE catalog files and merge them into one catalog at load time:

- `design/chunks.json` (the existing 25 chunks, unchanged location)
- `design/patterns-a.json` (T-070)
- `design/patterns-b.json` (T-071)

Each file has the same shape: `{ "version": 1, "patterns": [ ... ] }` for the two new files, while
`design/chunks.json` keeps its existing `{ "version": 1, "chunks": [ ... ] }` shape. The loader accepts
both key names. A missing file is not an error (the game must still run with only chunks.json).
Duplicate ids across files are an error reported by `validate-content`.

Add the two empty files `design/patterns-a.json` and `design/patterns-b.json` with
`{ "version": 1, "patterns": [] }` so the loader has something to read.

## Part 2 - the composition engine (`server/crates/sim/src/pattern.rs`, new module)

Add `pub mod pattern;` to `server/crates/sim/src/lib.rs`. Implement, with doc comments on every public
item:

- `PatternMeta`: the parsed metadata of one pattern (id, role, min_level, difficulty, theme tags,
  mechanic tags, hazard tags).
- `TagBag`: a seeded, tag-aware selection bag. It must:
  - never return the same pattern twice in a row;
  - strongly discourage returning a pattern seen in the last N picks (N configurable, default 6);
  - bias toward theme tags that are under-represented so far in the level, so a level has a coherent
    but varied theme mix;
  - be fully deterministic from a seed (no wall clock, no float transcendentals - the sim crate is
    compiled to WASM and must stay bit-exact).
- `CompositionPlan`: the ordered list of pattern ids a level will use, produced from
  `(seed, level, players)` before any geometry is placed.
- A function that turns a `CompositionPlan` into the existing assembly: the growth walk must draw its
  next chunk from the plan/bag instead of a fresh weighted pick, while keeping every existing
  acceptance rule (socket stitching, overlap, clearance, reachability validation).

Keep the existing behaviour when the catalog has no pattern metadata: fall back to today's
`chunk_weight` path so nothing regresses.

## Part 3 - the harness (`server/crates/sim/tests/patterns.rs`, new file)

- Run 1,000 seeds at several levels. Assert:
  - every generated level validates (the existing `validate` passes);
  - the same seed produces an identical level (reproducibility);
  - different seeds produce different levels (hard divergence): no two of the 1,000 share an identical
    ordered pattern list;
  - the immediate-repeat rate is zero and the within-6 repeat rate is below a threshold you justify;
  - theme-tag diversity per level is at least 2 distinct themes on average.
- Print a compact summary (repeat rates, distinct pattern lists, validation failures) so a human can
  read the numbers.

## Output format

Complete files with `=== FILE: <path> ===` ... `=== END FILE ===`, or single functions with
`=== FN: <path> :: <name> ===` ... `=== END FN ===`. Allowed paths:
`design/PATTERN_FORMAT.md`, `design/patterns-a.json`, `design/patterns-b.json`,
`server/crates/sim/src/pattern.rs`, `server/crates/sim/src/lib.rs`,
`server/crates/sim/src/levelgen.rs`, `server/crates/sim/tests/patterns.rs`.

Do not touch `web/`, `protocol/`, `design/chunks.json`, or any other crate. No new dependencies.

## Done when

`cargo test -p sim` passes including the new harness, `cargo clippy -p sim --all-targets -- -D warnings`
is clean, and `design/PATTERN_FORMAT.md` is complete enough that another agent can author 25 patterns
from it without asking a question. Put the harness numbers in NOTES.
