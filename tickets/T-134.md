# T-134 — Enemy registry coverage: a check that could never fail

**Cycle:** 14 · **Agent:** orchestrator · **Status:** PASS

## Why

T-132 closed the "pattern exists but never reaches a level" gap. The same question
applies to enemies: **can every enemy in the registry actually be voted for?**

The pattern audit has a metric for it — `6.enemy-frequencies.never-offered` — but it
was written as:

```js
line('6.enemy-frequencies.never-offered',
  neverList ? neverList.length === 0 : true, ...)
```

When the roster is absent it reports **PASS**. And the roster is *always* absent,
because the dump carries generic `spawn` markers, not enemy types — the type is
chosen at runtime from the registry. So the metric was a check that could never
fail, printed as a pass on every run. That is worse than no metric: it looks like
coverage.

## Change

### 1. The pattern audit now says SKIP, and says why

A new `skip()` line type reports neither pass nor failure and never enters `fails`.
`6.enemy-frequencies.never-offered` uses it when the roster is absent, and names the
check that *can* measure the thing:

```
SKIP - 6.enemy-frequencies.never-offered (the dump carries generic spawn markers,
not enemy types, so per-enemy placement is not measurable here; registry coverage is
asserted by economy-audit 3.pedestal_pool)
```

### 2. The economy audit asserts registry coverage, per mode

`3.pedestal_pool` already read the registry, so the check belongs there. Two new
conditions, evaluated for all four modes:

- **Every enemy must be reachable by level 20.** An enemy whose
  `min_level + mode.minLevelShift` exceeds 20 is a definition nobody can ever vote
  for. Level 20 is the depth the audit already uses for "a deep run".
- **Every enemy must have `selection_cap >= 1`.** A cap of 0 means the enemy can be
  offered but can never become permanent, which contradicts the voting contract.

Both name the offenders.

## Evidence — both checks have teeth

Degraded `design/content.json`: `pallbearer.min_level = 40`,
`snapshrike.selection_cap = 0`.

```
FAIL — 3.pedestal_pool
       standard: enemies unreachable by level 20: pallbearer@40
       standard: enemies with selection_cap < 1 (can never be permanent): snapshrike
       extreme: enemies unreachable by level 20: pallbearer@40
       ... (all four modes)
FAIL — economy-audit (7/8 metrics)
```

Reverted: `PASS — 3.pedestal_pool`, economy audit 8/8.

## Result

| | before | after |
|---|---|---|
| `6.enemy-frequencies.never-offered` | always PASS | **SKIP with a reason** |
| registry coverage | unchecked | **every enemy reachable by level 20, cap >= 1, all 4 modes** |
| pattern audit | 17 lines, 1 dead | **17 lines, 0 dead** |
| economy audit | 8/8 | **8/8** with 2 more conditions |

`just verify` green.

## Tuning notes

- The level-20 reachability floor is a judgement call. The deepest `min_level` in the
  registry is 12, so there is 8 levels of headroom. If a future cycle adds a
  level-25 enemy deliberately, this check should be raised with it — but it should be
  raised because someone decided to, not because the check was in the way.
- `selection_cap >= 1` is a contract invariant, not a balance knob. A cap of 0 would
  mean the voting contract's "the winner becomes permanent" is unachievable.

## Choice log

- **SKIP rather than delete.** The metric is meaningful when a roster *is* supplied
  (`PATTERN_AUDIT_ENEMY_TYPES`), and deleting it would lose that path. Reporting SKIP
  with a pointer to the real check keeps both.
- **Put the registry check in the economy audit, not the pattern audit.** The economy
  audit already reads `design/content.json`; the pattern audit reads a dump. Putting
  the check where the data is beats plumbing the data to the check.
- **Per mode, not once.** `extreme` shifts `min_level` by -1, so a mode-specific
  reachability bug is possible. Checking all four costs nothing.
