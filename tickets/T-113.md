# T-113 — Performance: make it less laggy

**Agent:** model:acpRegistry_mistral_vibe/deepseek-v4 (fresh thread)
**Owns:** performance-only changes. Anything that would change behaviour is
logged, not done.

## Method: measure, optimise, prove
1. **Profile** and record baseline numbers in this ticket:
   - server tick budget under a full 8-player simulation
   - client frame time and spike sources (draw calls, fog/telegraph effects,
     gift-count-heavy levels, WASM prediction cost)
   - load time
   - memory growth over a long run
2. **Optimise the measured hot paths only:** allocation churn in the tick loop,
   redundant re-renders, per-frame work that can be cached, effect LOD (distant
   fog/glow/telegraph fade), batched or instanced rendering where the pipeline
   allows, level-generation cost.
3. **Prove:** after/before numbers for every change. No change merges without a
   measured win.

## Known starting points from earlier cycles
- `web/public/sim.wasm` is 127,154 bytes (measured at `v0.20.0-alpha.1`).
- The client already instances platforms and ramps (`Platforms.tsx`), so the
  remaining draw-call cost is likely in enemies, gifts and effects.
- Gift-count-heavy levels are the obvious stress case: median 183 gifts per
  level, max 434.

## Done when
Baseline + after numbers documented per fix, frame spikes reduced measurably,
tick budget within target, zero behaviour regressions (full test suite
unchanged), gates green.

## Autonomous choices
- No target frame rate is invented here: the ticket records what the numbers are
  and requires each change to move them, rather than chasing an arbitrary budget.
