# T-154 — The playthrough bot, actuated through the debug layer

**Cycle:** 23
**Status:** PASS
**Area:** `tools/playthrough/run.mjs`, `tools/verify-live.mjs`

## The owner's decision

> PLAYTHROUGH BOT — fix it, and use the tester command layer as its actuators: a dev-flagged
> bot session that completes levels via the debug commands (level switch, gift grants, gold) is
> a legitimate way to restore level-progression / vote / shop E2E coverage. This bot is the
> backbone of every future audit, so it's worth real effort — but still inside the normal
> anti-rabbit-hole budget (3 attempts, then park).

## What was broken

Three checks in the sweep — `level-progression`, `vote`, `shop` — were gated on
`completed = maxLevel >= 2`, and the bots cannot complete a level. A greedy straight-line steer
cannot clear a gap it cannot probe, so `maxLevel` stayed at 1 and all three reported SKIP on
every run since T-139. A regression in the level → shop → vote chain would have gone unnoticed.

## The fix

`--actuate` runs a **singleplayer** session (the debug gate rejects every command at 2+
players) and drives the run through the frozen debug manifest while the bot keeps walking. The
frames the checks read are produced by a real session, not a mock.

The driver does three things, in the order a real run does them:

1. **Level progression** — `switch_level` to 2, then to 3. Each jump must produce a fresh
   `Level` frame with gifts on it and a `state` readout that agrees.
2. **Shop** — read the offer the jump generated, `set_phase` to `PHASE_ENEMY_DRAFT`,
   `grant_gold`, `Buy`, and prove the purchase landed by watching currency fall.
3. **Vote** — `grant_gift` until `gifts_left=0`, which opens the collapse window, then wait for
   `VoteOpen`.

`verify-live` now runs both passes: the 8-client protocol sweep, then the actuated one.

## Four measurement bugs found while building it

Each was caught by reading the numbers, not by trusting a green line.

**1. `level-progression` was passing on stale frames.** The server pushes its current run state
on `Hello`, and `Restart` only resets a run that is *over*. A server left at level 3 by an
earlier sweep therefore reported `highest level reached: 3` for a sweep that advanced nothing —
a PASS for work nobody did. The check now asks whether the level **changed** during the session
(`level went 1 -> 3`), not whether it is high. On a dirty server with a wrong dev code it
correctly reports `level went 3 -> 3` and SKIPs.

**2. The bot bought into a closed shop.** `react()` sent `Buy` on every `Shop` frame. But a
`Shop` frame is sent whenever the offer *changes*, including for a level that is already
playing, and the server answers a `Buy` outside `PHASE_ENEMY_DRAFT` with
`409 the shop is not open`. The `error-frames` check caught it. Auto-buy is gone: a purchase has
a precondition, so the driver sets it explicitly.

**3. The shop step deadlocked on its own capture point.** It recorded the log index *after* the
level jump and then waited for a new `Shop` frame — but the jump is what generates the offer, so
the frame had already arrived and the next one only comes after a purchase. No offer, no buy, no
new offer. The index is now captured before the jump.

**4. `draft` and `class-select` blamed the server for the sweep's own timing.** Both only exist
in the first lobby of a run. A sweep that joins a run already in progress cannot see either, by
design. Both are now gated on the precondition and SKIP with the reason instead of FAILing.

## Negative test

With `--code nope` the driver can do nothing, and every actuated check fails:

```
FAIL - actuate-shop (Shop frames: 1, items: 0, stocked: 0, no purchase landed)
FAIL - actuate-level-progression (level 2: ok=false freshLevel=false gifts=0 stateLevel=null; ...)
FAIL - actuate-vote (grant_gift failed: too many wrong codes)
SKIP - level-progression (level went 3 -> 3 (best client collected 66/66 gifts))
```

The rate limiter fired (`too many wrong codes`), and `level-progression` SKIPped rather than
false-passing — which is the stale-frame bug from #1, now provably fixed.

## What this does and does not prove

**Proves:** the level → shop → vote chain fires end to end. A level change regenerates the
world, re-prices the shop, and the shop accepts a purchase in the lobby phase; emptying a level
opens a vote with three options.

**Does not prove:** that a player can complete a level by walking. That still needs a faithful
JS port of the movement controller, and `gift-rate` remains the traversal check (30.7% this run,
floor 20%). The actuated pass reports `gift-rate` as SKIP with that reason rather than printing a
number that measures nothing.

## Choices made

- **A separate mode, not a flag on the 8-client sweep.** The debug gate is singleplayer-only, so
  the two passes cannot be the same session. `--actuate` forces one client.
- **`level-progression` is gated, not a hard FAIL.** The 8-client sweep genuinely cannot complete
  a level, so it SKIPs with the number that explains it. `--known-failures level-progression` is
  no longer needed to suppress it, and `verify-live` no longer passes it.
- **The driver runs concurrently with the bot**, not instead of it, so the session is a real one
  with real snapshots and real input frames.
- **No server change.** The debug layer already had every command this needed; the ticket is
  entirely in the tooling.
