# T-110 — Tester command layer: manifest + server

**Agent:** model:acpRegistry_mistral_vibe/deepseek-v4 (fresh thread)
**Dispatch FIRST of the two tester tickets.** T-111 consumes this manifest.

## 1. Frozen DEBUG COMMAND MANIFEST in `design/`
The contract for T-111. Per command: id, payload, effect. Minimum set:
- spawn enemy by registry id (count/position options)
- despawn all of a type
- switch level (jump to level N with chosen seed)
- grant gold (amount)
- grant/remove specific gifts
- set phase
- toggle fog density
- give/take any upgrade/curse
- trigger altar effects
- teleport players
- list current registry/pattern/vote state

## 2. Server implementation with JUDGMENT CALL 3 gating (hard rules)
- Commands exist ONLY when the server runs with the dev flag **OR** the request
  carries a valid dev code.
- The code comes from a server-side env var (`VOIDWRAP_DEV_CODE`), is verified
  **server-side**, and never ships inside client code.
- **SINGLEPLAYER ONLY:** the server rejects every command while more than one
  player is connected.
- Rate-limit wrong-code attempts.
- Audit log of every executed command.

## 3. Tests
Every command works with flag/code; rejected without both; rejected at 2+
players; wrong-code rate-limited.

## Done when
Manifest frozen, command layer implemented and tested, gating proven in all three
dimensions, gates green. **Merge the manifest before dispatching T-111.**

## Autonomous choices
- The dev code is an env var, not a build-time constant: a constant would ship in
  the client bundle, which the brief forbids.
- Singleplayer enforcement lives on the server, not the panel: a client-side
  check is a suggestion, a server-side check is a rule.

---

## Outcome — PASS

**Manifest frozen:** `design/DEBUG_COMMANDS.md`. 15 commands, each with id, owner
(server/client), args shape and effect, plus the three gates and the stable
refusal strings. Adding a command is additive; changing one is a human decision.

**Transport.** One protocol variant carries every command, so the wire format
stays small and the manifest — not the protocol — is the source of truth:

```
ClientMsg::Debug  { code: string, command: string, args: string }
ServerMsg::DebugResult { ok: bool, message: string }
```

`args` is a JSON object as a string. Generated through `just gen` + `just
fixtures`; two new golden fixtures (`client_debug`, `server_debug_result`).
PROTOCOL_VERSION stays 8 — the variants are appended, so an old client that
never sends `Debug` is unaffected.

**Gating, all three dimensions, all before the command is parsed** so a rejected
command has no effect at all:

1. *Availability* — `VOIDWRAP_DEV=1` or a code equal to `VOIDWRAP_DEV_CODE`.
   The code is read from the environment at startup, compared in constant time,
   and never leaves the server: not in the protocol, not in the client bundle,
   not in the manifest. An empty configured code is filtered in **both**
   constructors, so "empty code is never satisfiable" is a property of the type.
2. *Singleplayer* — rejected while `player_count() > 1`.
3. *Rate limit* — wrong codes counted per connection; at `MAX_BAD_CODES = 5` the
   connection is locked out for good, even with the right code. The count is
   dropped when the connection disconnects.

**Audit log.** Every executed command logs at `info` with conn, cmd, args, ok and
result; every refusal logs at `warn` with the reason.

**Implementation.** New `server/crates/server/src/debug.rs` (gate + dispatcher +
typed args reader). `run.rs` gained a documented `debug_*` block — the only entry
points the command layer uses, so it never reaches into private run state and
every debug effect goes through the same code path the real game uses
(`use_altar`, `rebuild_mods`, `start_level`, `spawn_enemy_with`). `game.rs` gained
the `Gate` field, the `Debug` arm and the disconnect hook.

**Choices made without a human.**
- *One variant, JSON args* rather than 15 protocol variants: keeps the frozen
  protocol surface at two additions and puts the contract in a document a human
  can read.
- *Unknown args keys are errors*, not silent no-ops: a tester who mistypes must
  find out.
- *`set_fog` is a client-owned command.* Fog is a client-side visual with no
  server state; the server validates the range and gates it, the panel applies it.
- *`switch_level` keeps the run.* Currency, permanents, curses and upgrades
  survive a level jump; only the level's own state resets. A tester jumping to
  level 30 wants level-30 content with their current build, not a fresh run.
- *`spawn_enemy` does not enforce the registry selection cap.* The cap governs
  the vote pool, not a tester's ability to put 20 LUREs on screen; enforcing it
  would make the panel useless for stress testing. Documented in the manifest.

**Tests.** 8 in `debug.rs` (gate matrix, rate limit, empty-code hole, constant-time
compare, unknown key, unknown command) + 7 in `game.rs` (closed route, dev flag,
dev code, singleplayer rejection and reopening on disconnect, rate limit, spawn/
despawn round trip, level jump preserving the run). 147 server tests total.

**Gate.** `just verify` green: 147 server tests, 286 vitest, clippy `-D warnings`,
`cargo fmt --check`, protocol-gen `--check`, validate-content 132 patterns,
check-names 609 files.
