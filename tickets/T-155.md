## What was broken

`6.enemy-frequencies.never-offered` and `6.enemy-frequencies.always-offered` had both been
SKIPped since T-134 and T-148 respectively. The reason was structural, not a bug in the metric
code: the level dump emits `enemies: [{"type":"spawn"}]` — generic markers, because the enemy
type is chosen at runtime from the pool — so a metric that asks "which enemies are offered"
was reading a field that can never carry the answer.

The pool logic (`vote_pool_with`, `PoolEntry`, `permanent_tag_counts`, `requires_satisfied`,
`class_excluded`) lives in `server/crates/server/src/run.rs`. The level dump lives in
`server/crates/sim/examples/pattern_dump.rs`. The owner's ruling forbids moving either.

## The fix

**The pool gets its own dump, in the crate that owns it.** `voidwrap-server --dump-pool` prints
one NDJSON record per (mode, level) and exits before `startup()`, so it never touches the
network or the web directory:

```json
{"mode":"standard","level":10,
 "pool":["pallbearer","moteling","rewind", ...],
 "gated":[{"id":"chorus","requires":[{"tag":"small","count":2}],"satisfiable":true}]}
```

120 records: 4 modes x 30 levels. The table is the **fresh** pool — no permanents held, no class
picks — which is the state every run starts from and the only one reproducible without
simulating a run.

**`gated` is the part that matters.** `chorus` is held back by a `requires` hook (2x `small`
permanents) and never appears in a fresh pool. Without a `gated` list it would read as dead
registry content. Each gated entry carries its requirement and a `satisfiable` flag computed
where the tag data lives: true when every requirement can be met by entries that are themselves
ungated at that level. `selection_cap` is >= 1 for every registry entry, so holding one of each
is always possible.

**The audit joins the two dumps by (mode, level).** `--pool <path>` (or `PATTERN_AUDIT_POOL`):

- `6.enemy-frequencies.never-offered` — every roster enemy must appear in some pool, or be gated
  with a satisfiable requirement. An enemy that is gated with an *unsatisfiable* requirement
  fails, because that is dead content.
- `6.enemy-frequencies.pool-depth` — **replaces `always-offered`.** That metric asked whether a
  type appeared in 100% of a cell's levels, which for a *pool* is true by construction for any
  low-`min_level` enemy — the pool only grows — so it could only ever fire on a defect that is
  not one. Pool depth is the question that matters: a vote needs three options, so a cell with
  fewer than three cannot build one. Measured at every level, not the 1/10/20 sample
  `economy-audit 3.pedestal_pool` uses.

Both metrics SKIP when no pool table is supplied, and FAIL when the table is empty. Neither can
report PASS on an empty denominator.

## Result

`--selftest` plants four defects and proves the gate path both ways:

```
FAIL - 6.enemy-frequencies.never-offered (roster types no (mode, level) pool can ever offer:
       ghost, gated-bad of 6; gated but reachable: gated-ok (2x small);
       gated with an unsatisfiable requirement: gated-bad; threshold: 0)
FAIL - 6.enemy-frequencies.pool-depth ((mode, level) cells whose vote pool holds fewer than 3
       options: 1 of 3 (standard@3: 2); depth range 2-3; threshold: 0)
SELFTEST - PASS
```

`gated-ok` is gated with a satisfiable requirement and correctly does **not** fail.

Real run, 400 seeds (6,000 levels) + the live pool table:

```
PASS - 6.enemy-frequencies.never-offered (roster types no (mode, level) pool can ever offer:
       none of 20; gated but reachable: chorus (2x small);
       gated with an unsatisfiable requirement: none; threshold: 0)
PASS - 6.enemy-frequencies.pool-depth ((mode, level) cells whose vote pool holds fewer than 3
       options: 0 of 120; depth range 3-19; threshold: 0)
RESULT: PASS - 0 of 17 metric lines failed
```

The pattern audit went from **17 lines, 0 failed, 2 skipped** to **17 lines, 0 failed, 0 skipped**.
Both retired SKIPs are now live checks.

## What the numbers say

- Pool depth runs 3 (level 1, every mode) to 19 (level 29-30, Random). The floor is exactly 3,
  which is exactly what a vote needs — no headroom, but no shortfall either.
- `chorus` is the only gated enemy, and its gate opens at level 10 with 4 `small` candidates
  available (moteling min 1, lantern_leech min 2, snapshrike min 3, mimic min 3).
- Every one of the 20 registry enemies is reachable. Nothing is dead stock.

## Choices made

- **A CLI flag, not an example.** The `server` crate is binary-only (`[[bin]] name =
  "voidwrap-server"`, no lib target), so `server/examples/` cannot `use server::...`. A flag on
  the binary is the only place the pool logic can be reached from outside.
- **`serde_json::json!` for the record, not hand-rolled escaping.** The first attempt built the
  JSON with `format!` and escaped quotes; the escaping survived review but the approach is a
  trap for the next edit. `json!` removes the class of bug.
- **`always-offered` retired rather than repaired.** It was measuring a property that is true by
  construction. Repairing it would have meant inventing a threshold for a non-defect.
- **The roster comes from `design/content.json` in `verify-live`.** A new enemy that never
  reaches a pool now fails the audit instead of silently missing from the check.
- **A unit test asserts the same rule as the audit.** `pool_table_covers_every_mode_and_level`
  checks record count, pool depth >= 3, and that no registry enemy is stranded — so a content
  edit that strands one fails `cargo test`, not only the live gate.
