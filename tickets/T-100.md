# T-100 — Normalize the ten oversized/undersized patterns to the reference footprint

**Agent: `model:opencode/opencode/inkling-2-small-free` (max effort).**

You have no tools. Everything you need is in this ticket. Reply with the blocks
described in §5 and nothing else.

## 1. Context

VOIDWRAP generates levels by stitching **patterns**: data fragments of platforms,
sockets and slots. The format is frozen in `design/PATTERN_FORMAT.md`; you are not
changing the format, only the geometry inside ten existing patterns.

The pattern audit measures each placed pattern's **max XZ footprint extent** — the
larger of `max_x - min_x` and `max_z - min_z` over all of its platforms. The reference
band is **[10, 20] world units**. Ten patterns sit outside it. Six of them are too
wide (21–30u), four are too narrow (8.5u).

A mechanical scale was already tried and rejected: scaling a pattern shrinks its
ramps below the minimum run and width, which fails the ramp audit with thousands of
violations. **You must redesign each pattern by hand**, not scale it.

## 2. The task

For each of the ten patterns in §4, edit its `platforms` array (and, where a platform
moves, the `sockets`, `gift_slots`, `enemy_slots`, `altar_slots` and `beacon` that sit
on it) so that the pattern's max XZ footprint extent lands inside **[10, 20]**.

Aim for **20** on the oversized ones and **10** on the undersized ones. Anything
strictly inside the band is accepted, but do not stop at 20.5 or 9.9.

## 3. Hard rules — a violation fails the ticket

1. **Ramps keep their exact run and width.** For every platform whose `kind` is
   `RAMP_PX`, `RAMP_NX`, `RAMP_PZ` or `RAMP_NZ`:
   - `run` = the extent along the ramp's travel axis, **>= 2.0**
   - `width` = the extent along the other horizontal axis, **>= 3.0**
   - `rise / run <= 0.5`, where `rise` = `max_y - min_y`
   Do not change a ramp's `min`/`max` along its travel axis or its width axis. You may
   **move** a ramp (translate it) but not resize it.
2. **Every socket, gift slot, enemy slot, altar slot and beacon must stay on a
   platform.** After your edit, each `pos` must lie within the XZ bounds of at least
   one platform, and its `y` must equal that platform's top (`max_y`).
3. **Do not change** `id`, `name`, `role`, `min_level`, `difficulty`, `tags`, or the
   number of platforms. Do not add or remove platforms.
4. **Do not change any pattern not listed in §4.**
5. **No new files, no new tags, no new platform kinds.**
6. Coordinates are metres, rounded to at most 3 decimals. Keep `y` values as they are
   unless a rule above forces a change.

## 4. The ten patterns

Each entry shows the pattern's current extent and its full current JSON. `file` is
where it lives; you do not need the rest of the file.

## 5. Output format

Reply with **one block per pattern**, in the order of §4, and nothing else. No prose
before, between or after the blocks.

```
=== PATTERN: pa_void_catwalk ===
{
  "platforms": [ ... ],
  "sockets": [ ... ],
  "gift_slots": [ ... ],
  "enemy_slots": [ ... ],
  "altar_slots": [ ... ],
  "beacon": [x, y, z] | null
}
```

Rules for the block body:

- It is a JSON object. It must parse.
- Include **every** key the original pattern has among `platforms`, `sockets`,
  `gift_slots`, `enemy_slots`, `altar_slots`, `beacon`. If the original has no
  `enemy_slots`, omit it; do not invent one.
- Do not include `id`, `name`, `role`, `min_level`, `difficulty` or `tags` — those are
  unchanged and the orchestrator keeps the originals.
- The `platforms` array must have the same length and the same `kind` sequence as the
  original.

## 6. How this is checked

The orchestrator will, for each block:

1. Parse the JSON. A parse error fails the ticket.
2. Splice it into the pattern, keeping `id`/`name`/`role`/`min_level`/`difficulty`/`tags`.
3. Recompute the max XZ footprint extent and require `10 <= extent <= 20`.
4. Re-check every ramp against rule 1 and every slot against rule 2.
5. Run `node tools/validate-content.mjs` and the pattern audit; `5.ramps` must stay at
   0 violations and `5.reference-scale` must improve.

If a pattern cannot be brought into the band without breaking rule 1 or rule 2, say so
in a single line `=== PARK: <id> — <reason> ===` instead of a block, and do the rest.

## 7. Done when

All ten patterns are either inside `[10, 20]` or explicitly parked with a reason, and
every block you emit satisfies §3.
