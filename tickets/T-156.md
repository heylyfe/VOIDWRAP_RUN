# T-156 — The bot walks: two real bugs fixed, level completion still parked

**Cycle:** 24
**Status:** PARTIAL — the walking bugs are fixed and measured; emptying a level by walking is PARKED
**Area:** `tools/playthrough/run.mjs`, `server/crates/server/src/main.rs`

## The owner's decision

> 2. Bot completes a level by WALKING — the last dark corner and the priority item of this cycle.
>    A real level-completion E2E closes the biggest coverage hole we have; gift-rate at 30.7%
>    means traversal works, but nothing yet proves a level can be finished.

## What was actually wrong

The bot had been blamed for two cycles on "a greedy straight-line steer cannot clear a gap it
cannot probe". That was not the bug. Two measurement bugs were, and both were invisible from the
outside because the bot's symptom was always the same: it fell off the map.

### Bug 1 — the bot fed the server 80 input frames per second

`startWalking` sent **4 frames every 50 ms** = 80 frames/s. The server drains
`PHYSICS_HZ / TICK_HZ = 60 / 20 = 3` frames per 20 Hz tick = **60 frames/s**. The queue filled to
`MAX_QUEUED_INPUTS` (60 frames = one full second) and then dropped the excess, so **every input
the bot sent was applied about a second late**.

That is why the bot could see an edge, press jump, and still fall. The trace showed it exactly:

```
{"x":0.208,"grounded":true,"edge":0.6,"landing":3.45,"jump":true}
{"x":-0.057,"grounded":true,"edge":0.15,"landing":3.15,"jump":true}
{"x":-0.537,"y":-0.009,"grounded":false,...}          <- already falling
```

Two consecutive jump presses, and the jump never fired, because the press arrived after the bot
had left the platform.

**Fix:** send at the physics rate — one frame every `1000 / PHYSICS_HZ` ms. The queue neither
backs up nor starves.

### Bug 2 — air control aimed at the point directly below the bot

```js
if (!you.grounded) {
  const landing = this.nearestLanding(pos.x, pos.z, pos.y);
  if (landing) { aimX = landing.x; aimZ = landing.z; }
}
```

`nearestLanding` returns the nearest point on any platform at or below the bot. For an airborne
bot over a platform that is **the point directly below it**, so `aimX/aimZ` became the bot's own
position, `dirX/dirZ` became `(0, 0)`, and the bot had **no horizontal control in the air at
all**. It could not cross a gap it had just jumped.

Measured: **2715 of 3431 steer frames (79%) had a degenerate aim, every one of them airborne.**

**Fix:** keep the ground aim unless the landing is more than 0.5 u away, which is the case that
actually needs correcting. After the fix: **0 degenerate frames in 818**.

## Three smaller fixes, each measured

- **Edge probe.** The old check probed one fixed distance (0.9 u) and jumped at any landing up to
  5.5 u away. 5.5 u is outside the jump envelope for any rise above ~0.3 u, so the bot jumped at
  gaps it could not clear. It now measures the edge distance in 0.15 u steps and only accepts a
  landing inside `jumpReach(rise)`, computed from `tuning.rs` (`JUMP_VELOCITY 12`, `GRAVITY 32`,
  `RUN_SPEED 9`, `JUMP_SAFETY 0.75`).
- **No bunny-hopping.** The `rise > 0.3` climb heuristic was true nearly every frame (gifts are
  almost never at exactly the bot's height), so the bot jumped constantly with no control over
  where it landed. Climbing is already covered by the deliberate edge jump, which accepts a
  landing up to `JUMP_APEX - 0.2` above the launch point. Removed.
- **`safeToJump`.** A jump travels `jumpReach(0)` ≈ 5 u, so the unstick jump is only allowed when
  the ground continues that far. The trace showed a `stuck` jump from z=-6.8 that carried the bot
  6.7 u to z=-0.1 with nothing underneath.
- **`nearestOn` inset.** The route aim returned the bot's own position whenever it stood on the
  boundary between two platforms, so the aim became `(0, 0)` and it stood still. Now inset 1 u
  inside the next platform.

## New: `VOIDWRAP_SEED`

Every run used a clock seed, so two playthrough runs generated **different levels** and no
gift-rate or death count could be compared across runs. That is how the input-rate bug survived
several "it got better" readings that were really just easier levels. `VOIDWRAP_SEED` pins it,
same family as `VOIDWRAP_START_LEVEL`, and warns when set.

## New: `--trace`

Per-steer NDJSON: position, grounded, target, aim, direction, edge distance, landing distance,
jump, stuck count. A death log says where the bot landed; this says what it saw and decided. Every
finding above came from reading it.

## What is still parked, and why

**The bot still cannot empty a level.** It survives, it moves (438 distinct positions in the last
60 s of a run), and it collects half the gifts — but the remaining half are gifts it has no route
to. The trace shows the bot spending most of its time with **every remaining gift blacklisted**,
holding still until the 3 s blacklist expires.

The missing piece is **vertical routing**: a gift directly above or below the bot has no route.
The bot's platform graph is horizontal-only, and `platformUnder` collapses the gift's platform to
the bot's own when they share a footprint. Two attempts at a shortcut both measured worse and were
reverted:

- jump when the aim is degenerate → **14/46 and a void death** (the jump fires wherever the bot
  happens to be standing, including at an edge);
- blacklist when the aim is degenerate → **9/46** (it blacklists gifts that are reachable, because
  the aim degenerates transiently).

A real fix is a 3D route: pick the platform the gift is on, walk to a point under it, then jump.
That is a rewrite of the routing, not a polish, and it is outside this cycle's budget.

**Logged as a known coverage hole for the next audit.** `level-completion` is now its own check in
the sweep: SKIP today with the number and the reason, a live PASS the moment a level is emptied by
walking. It is not a FAIL, because a permanently red line trains the gate to be ignored.

## Choices made

- **The input rate is a protocol fact, not a heuristic.** `STEPS_PER_TICK` is derived from
  `PHYSICS_HZ / TICK_HZ` in the tool, so a future tick-rate change moves the bot with it.
- **`level-completion` SKIPs rather than FAILs.** It is a coverage hole, not a regression. The
  detail carries the number so the gap is visible in every gate run instead of being remembered.
- **`VOIDWRAP_SEED` is a dev/QA aid, not a gameplay feature.** It warns on startup like
  `VOIDWRAP_START_LEVEL` does.
- **The two failed shortcuts are documented in the code**, not just in this ticket, so the next
  person does not re-try them.
