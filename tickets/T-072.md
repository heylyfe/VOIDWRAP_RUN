# Ticket T-072: enemy registry contract (frozen spec + data migration)

Small but load-bearing: T-074, T-075, T-078, T-080 and T-085 all read this registry. Get the shape
right and freeze it.

## What exists (verified)

- `design/content.json` has an `enemies` array of 9 entries:
  `{ "id", "name", "flavor", "behavior" (prose), "threat" (1..5), "params": { "speed", "aggro",
  "grace_s", "size", "behavior" } }`.
- `server/crates/server/src/content.rs` parses it into `EnemyDef { id, params: EnemyStats }`.
- `server/crates/sim/src/rules.rs` defines `BEHAVIOR_*` constants (0..8) and `EnemyParams
  { behavior, speed_mul, size, grace_ticks }`, plus one brain per behaviour.
- `tools/check-names.mjs` enforces the plain-names convention on content names.
- `tools/validate-content.mjs` validates the content file.

## Part 1 - the frozen registry spec (`design/ENEMY_REGISTRY.md`, new file)

Write the binding spec. Every enemy, existing and new, gets exactly one registry entry with:

- `id` (stable, lowercase, matches the content id), `name` (plain, what-it-does, check-names green).
- `cue_tier`: 1 = under 1 s telegraph (instant dodge), 2 = 1-2 s (reposition), 3 = ambient
  (awareness only). Define what each tier obliges the implementation to show.
- `min_level`: the first level the enemy may be offered.
- `selection_cap`: how many permanent copies may exist in one run (1 or 2).
- `tags`: from a closed vocabulary you define (e.g. `fog`, `ambush`, `collapse`, `chase`, `zone`,
  `debuff`, `summon`, `small`, `large`).
- `class_interactions`: which of the 5 classes counter it, are immune to it, or never attract it.
  The classes are Striker, Grappler, Bulwark, Glider and the fifth in `design/content.json` - read it.
- `synergy_hooks`: DECLARATIVE data, not code. A hook names another enemy id and the effect, e.g.
  `{ "with": "coil", "effect": "peal_lethal_when_overtuned" }`. Define the closed set of effect names
  the engine will understand.
- `params`: the existing speed/aggro/grace/size/behaviour block, unchanged.

Also define the POOL RULES the voting system will use: how `min_level`, `selection_cap`, current
permanent count and class composition filter the candidate list, and what happens when the pool is
empty (overflow: temporary enemies).

## Part 2 - migrate the existing 9 enemies

Add the new fields to all 9 entries in `design/content.json` with sensible values derived from their
current `threat` and behaviour. Do not rename anything that check-names already accepts. Do not change
their `params`.

## Part 3 - the 11 new entries (data only, no behaviour)

Add registry entries for the 10 pre-approved designs plus LURE. Behaviour is implemented in T-074 and
T-075; you only add the data. Use exactly these ids and names, and these parameters:

| id | name | cue | min_level | cap | tags |
|---|---|---|---|---|---|
| rewind | Rewind | 2 | 1 | 2 | chase, zone |
| warden | Warden | 2 | 2 | 1 | chase, loot |
| peal | Peal | 1 | 4 | 1 | zone, debuff |
| kite | Kite | 2 | 6 | 1 | chase, zone |
| static | Static | 3 | 5 | 2 | fog, chase |
| blight | Blight | 3 | 8 | 1 | debuff, chase |
| metronome | Metronome | 1 | 10 | 1 | zone, debuff |
| overlook | Overlook | 2 | 12 | 1 | zone, chase |
| chorus | Chorus | 3 | 10 | 1 | summon, small |
| coil | Coil | 1 | 4 | 2 | zone, debuff |
| lure | Lure | 1 | 3 | 2 | fog, ambush, collapse |

Synergy hooks to record: `peal` with `coil` (overtuned makes Peal lethal); `blight` with `rewind` and
`kite` (infection pauses their timers); `chorus` requires two `small` permanents and level >= 10.

## Part 4 - parser and validation

- Extend `server/crates/server/src/content.rs` so the new fields parse, with `#[serde(default)]` on
  every new field so an older content file still loads.
- Extend `tools/validate-content.mjs` to check: unique ids, `cue_tier` in 1..3, `min_level` >= 1,
  `selection_cap` in 1..2, every tag in the closed vocabulary, every synergy `with` naming a real
  enemy id, and every `effect` in the closed set.
- Add a Rust unit test that the shipped `design/content.json` parses and that all 20 entries are
  present with valid values.

## Output format

Complete files with `=== FILE: <path> ===` ... `=== END FILE ===`, or single functions with
`=== FN: <path> :: <name> ===` ... `=== END FN ===`. Allowed paths:
`design/ENEMY_REGISTRY.md`, `design/content.json`, `server/crates/server/src/content.rs`,
`tools/validate-content.mjs`.

Do not touch `web/`, `protocol/`, `server/crates/sim/`, or any other crate. No new dependencies.

## Done when

`node tools/validate-content.mjs` passes, `node tools/check-names.mjs` passes,
`cargo test -p server` passes, and the spec is complete enough that T-074 and T-075 can implement
behaviour from it without asking a question. Note in NOTES any value you had to invent.
