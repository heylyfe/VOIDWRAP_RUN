# T-121 — Playthrough bot: make it actually navigate

**Cycle 11, refinement 1 of 4.** Highest measured impact in the backlog: the
playthrough kit is the only end-to-end test in the repo, and **4 of its 11
checks are permanently SKIP** because the bot never completes a level.

```
SKIP - level-progression (highest level reached: 1)
SKIP - draft             (Draft frames: 8)
SKIP - vote              (VoteOpen frames: 0)
SKIP - shop              (Shop frames: 0)
```

`draft` and `vote` are skipped *even though frames arrived* — the gate is
`completed ? ok : null`, so one dead check darkens three live ones.

## Root cause — three bugs, all in `tools/playthrough/run.mjs`

The bot already has a `steer()` that aims at the nearest uncollected gift. It
does not work, for three independent reasons.

### 1. It never jumps

```js
} else if (msg.variant === 'Snapshot') {
  this.pos = msg.you && msg.you.pos ? msg.you.pos : null;
}
```

`this.pos` is the bare `Vec3`. `steer()` then reads `pos.grounded`:

```js
jump: Boolean(pos.grounded) && (rise > 0.3 || len > 2.0),
```

`Vec3` has no `grounded` field — it lives on `ControllerState`, one level up.
So `pos.grounded` is `undefined`, `Boolean(undefined)` is `false`, and **the
jump button is never pressed**. A bot that cannot jump cannot climb a ramp,
cannot cross a gap, and cannot reach a gift on a higher platform.

**Fix:** keep the whole controller state (`this.you = msg.you`) and read
`this.you.grounded`.

### 2. It re-steers to gifts it already took

`Snapshot` carries `gifts_taken: Vec<u16>`. The bot never reads it. Its own
`collected` set is only ever filled by the heuristic below, so after a gift is
picked up the bot keeps walking back to it — the nearest gift is usually the
one it just took.

**Fix:** union `msg.gifts_taken` into `this.collected` on every snapshot.

### 3. It gives up 2.4x too early

```js
if (bestD < 2.25) this.collected.add(best.id);   // bestD is squared distance
```

That abandons a gift at **1.5 u horizontal**. The real pickup test is
`rules::gift_touched_within`, which compares the player *centre* (feet + 0.9)
to the gift centre within `GIFT_RADIUS = 1.1`. At level height that leaves
`sqrt(1.1^2 - 0.9^2) = 0.63 u` of horizontal tolerance. The bot walks away
from gifts it is still 0.87 u too far from.

**Fix:** abandon only when the server says the gift is taken (bug 2's fix), and
keep a small safety radius well inside the real one.

### 4. No stuck detection

A bot that walks into the side of a platform pushes against it forever. The
straight-line steer has no notion of an obstacle.

**Fix:** track position over a window; if it has not moved while steering,
jump and blacklist that gift for a few seconds so the bot tries a different
one. This is not pathfinding — it is enough to get off a wall.

## What this is not

Not a port of the movement controller. The server simulates; the bot only
sends `Inputs`. It needs to *aim*, not to *predict*. That is why this is a
small diff and not the multi-day job F-115-8 assumed.

## Done when

- `level-progression` passes: the bot reaches level 2+ inside 60 s with 8
  clients.
- `draft`, `vote`, `shop` become live checks (PASS or FAIL, never SKIP).
- `--known-failures level-progression` is removed from `tools/verify-live.mjs`
  and from the `just verify-live` path.
- `just verify` green, `just verify-live` PASS with **no** known failures.

## Tuning notes

- 8 clients all steering at the same nearest gift is a thundering herd. If
  level completion is slow, stagger each client's target by index before
  reaching for pathfinding.
- The 60 s window is a harness budget, not a game constraint. If a level
  legitimately takes longer than 60 s to clear with 8 bots, raise the window
  rather than loosening the check.

## Outcome — partial, merged

**Fixed: the kit could not see gift state at all.** `tools/voting-conformance/wire.mjs`
decoded `Snapshot` only as far as `you` and stopped, with a comment saying
callers that need more must extend it. Nothing did. So `msg.gifts_taken` was
always `undefined`, the bot's `collected` set never grew, and it walked back to
the gift it had just picked up — forever. The decoder now skips `players` and
`enemies` by size (`PLAYER_VIEW_BYTES = 30`, `ENEMY_VIEW_BYTES = 36`, both
derived from the generated structs) and reads `gifts_taken`. This is a harness
bug, not a game bug: the server was collecting gifts correctly the whole time.

**Fixed: the bot never jumped.** `this.pos` was the bare `Vec3`; `grounded`
lives on `ControllerState`. `Boolean(undefined)` is `false`, so the jump button
was never pressed.

**Fixed: the bot walked off the level.** The first working version steered in a
straight line and the server logged `player out; spectating cause=0`
(`DEATH_VOID`) for every client. `groundAt()` now probes one step ahead against
the platform AABBs (ramps count along their whole incline) and either jumps at a
landing inside jump range or gives up on that gift.

**Fixed: greedy oscillation.** Nearest-target selection flipped direction every
frame — the velocity trace reversed sign every second. Hysteresis keeps the
current target until it is collected, blacklisted, or something is 4x closer.

**Fixed: jump spam.** `len > 2.0` made the bot jump whenever the gift was more
than 2 u away, which is always; a bot that jumps every frame never builds
horizontal speed. It now jumps only for a rise, a gap, or being stuck.

**Fixed: stuck detection ran at the wrong rate.** It compared against the
previous `steer()` call, but `steer` runs at the input rate and snapshots at the
tick rate, so "no new snapshot yet" counted as "did not move". Moved into the
snapshot handler.

**Result:** the bot collects **39 of 88 gifts** in 60 s (was 0), and `draft` is
now a live check instead of a SKIP — it fires before level 1, so it never needed
a completed level. Playthrough went from **7 pass / 3 skip / 1 fail** to
**8 pass / 2 skip / 1 fail**.

## Parked: `level-progression`, `vote`, `shop`

The collect phase ends only when **every** gift is collected
(`run.rs:2156`, `if self.normal_left() == 0`). There is no timer. A greedy
straight-line bot cannot clear 88 gifts across 75 platforms with gaps, and one
fall ends that bot for the level.

The next step is a **BFS over the platform graph**: nodes are platforms, edges
are pairs whose edge-to-edge gap and rise fit `design_max_gap`, and the bot
walks to the shared edge before jumping. That is a real pathfinder, not a
tuning change, so it is parked rather than half-built. `vote` and `shop` stay
gated on completion until then.

`--known-failures level-progression` therefore stays in `tools/verify-live.mjs`.
