# Ticket T-055 r2: make the physics bot navigate the big layered maps
Target: INKLING (max effort)

The assembler now works (all sample maps valid, 65-280 platforms, heights -10..+12; 18 levelgen tests pass) and the
controller gained step-up (0.55 u), jump pads and the rest of T-052 (all controller tests pass). But the physics bot in
`server/crates/sim/tests/playthrough.rs` was written for flat single roads: it heads straight for a target platform
and gets stuck against obstacles, e.g. "bot stuck at (10.5, 0.5, 8.2) heading to platform 42" (on the spawn hub's
raised beacon dais), "stuck at (8.1, 2.2, 8.1) heading to platform 45/16/0" (hub corners / near pillars / stairs).

## Task
Rewrite the bot's navigation (keep the real controller for all movement - the point is proving the maps are
playable with real physics):
1. Build the same platform graph as `levelgen::validate` (expose it from levelgen with an FN edit if useful:
   e.g. `pub fn platform_graph(level: &LevelData) -> Vec<Vec<usize>>` + doc comment) and plan a platform-to-platform
   route with BFS from the bot's current platform to the target platform.
2. Walk the route edge by edge: for a walk/step edge (touching, rise <= 0.55 u) steer to the closest point on the
   shared edge then onto the next platform's interior; for a jump edge run up to a takeoff point on the current
   platform's edge facing the next platform and jump (reuse the existing hop commitment logic); for a jump-pad edge
   walk onto the pad and steer toward the target while airborne. Steer around nothing else - edges already avoid
   obstacles because the route stays on platform tops.
3. Keep the test feasible: 10 seeds x levels 1..6, 8 seed-chosen gifts then the beacon; per-goal frame budget as
   today; on failure print seed, level, current platform, next platform, edge kind.
4. If the bot finds a real map defect (an edge the graph says exists but physics cannot do), report it in NOTES with
   the seed/level/platforms - do not paper over it.
