# T-132 — Catalog coverage: every pattern must reach a level

**Cycle:** 14 · **Agent:** orchestrator · **Status:** PASS

## Why

Three separate bugs in this project have shipped the same defect: a piece that
parses, validates, is counted by `validate-content`, and **never reaches a level**.

| bug | how it was found |
|---|---|
| `platform_kind_from_str` never learned `"TRIPMINE"` | T-123, by hand |
| `verify_socket` rejected ramp edges, dropping `ch05_ramp_of_embers` | T-123, by hand |
| `mech:fork` on a two-socket path made `pa3_mine_switchback` permanently ineligible | T-129, by noticing 0 placements |

The first two are caught by `every_shipped_chunk_parses_strictly`'s count
assertion. The third is invisible to it — the piece *is* in the catalog, it is
simply never chosen. And it is invisible to every metric in the pattern audit too,
because a piece with no placements contributes to no rate.

## Change

`tools/pattern-audit/run.mjs` gains metric **`7.catalog-coverage`**:

1. Reads every pattern id from `design/chunks.json` and `design/patterns-*.json`
   directly (the audit already lives in the repo; it does not need the dump to
   carry the catalog).
2. Collects every id that appears in at least one generated `plan`.
3. Fails if any catalog id never appears, and names up to twelve of them. Also
   fails on the reverse — an id in a plan that is not in the catalog — which would
   mean the dump and the design files disagree.

Returns SKIP rather than FAIL when `design/` is unreadable, so a checkout with only
a dump still runs.

## Evidence — the gate has teeth

Negative test: appended a deliberately ineligible pattern (`mech:fork` on a
`path` role, the exact T-129 bug) to `design/patterns-b.json` and re-ran the audit
against the same dump.

```
FAIL - 7.catalog-coverage (catalog patterns: 141; reached at least one plan: 140;
never placed: 1 (pb_negative_probe); placed but not in the catalog: 0;
threshold: 0 never-placed)
RESULT: FAIL - 1 of 17 metric lines failed: 7.catalog-coverage
```

Reverted, same dump:

```
PASS - 7.catalog-coverage (catalog patterns: 140; reached at least one plan: 140;
never placed: 0; placed but not in the catalog: 0; threshold: 0 never-placed)
RESULT: PASS - 0 of 17 metric lines failed
```

Pattern audit **16/16 -> 17/17**. `just verify` green.

## Tuning notes

- The metric needs enough seeds to be meaningful: at 400 seeds x 3 modes x 5 levels
  every one of the 140 patterns is placed, but a much smaller dump could produce a
  false failure on a high-`min_level` piece. `verify-live` uses 400 seeds, which is
  the same dump the other metrics use, so this is consistent.
- If a future cycle adds a pattern with `min_level` above the deepest level the dump
  generates, this metric will fail. That is correct — a piece nobody can reach is
  the bug — but the fix is to lower `min_level`, not to raise the seed count.

## Choice log

- **Read `design/` from the audit, not from the dump.** Adding a catalog record to
  the NDJSON would have changed the dump's contract for one metric. The audit is a
  repo tool; reading the repo is what it already does for its vocabularies.
- **Fail on unknown ids too.** A plan id that is not in the catalog means the dump
  and the design files have diverged, which is worth failing on for the same reason.
- **SKIP, not FAIL, when `design/` is missing.** The audit is documented to run
  against a dump alone; breaking that would be a regression in the tool.
