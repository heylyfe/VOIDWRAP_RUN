# Ticket T-050: M3 game design - enemy roster rework, new class, modular maps, gifts + collapse
Target: INKLING (max effort) - DESIGN ticket (no code)

## Context
VOIDWRAP RUN is an original roguelite 3D collectathon platformer: players collect gifts on floating checkerboard
platforms in a misty coloured void while enemies they voted for hunt them; golden gifts are the team's currency; a
beacon ends the level; cards (upgrades/curses) and a lobby shop shape the run; 1-8 players, server-authoritative,
20 Hz server ticks, deterministic 60 Hz player controller shared with the client.

The human's feedback after playing alpha 2 (this ticket must answer all of it):
1. "There should be way more gifts: around 50 on the first round, smaller. On the second gift round all the old gifts
   get replaced with new golden ones that are the currency."
2. "Make the enemies actually different from each other and not just copy cats" and "make them look a bit better".
3. "The blinker class is just striker but a bit better - rework it or create a new one."
4. "The maps need a lot of work. There is no elevation, it is always flat. Create around 25 different map variations
   that can connect and stack together like a puzzle. Some paths are way too narrow."

A researcher studied a game in the same genre; the notes are below. Use them ONLY for principles (two-phase level,
distinct demanded skill per enemy, telegraph rules, lethal + non-lethal mix, attack mutex, escalation events, etc.).
HARD RULE: our content must be original - do not reuse that game's names, and do not clone any single enemy, class,
item or level from it 1:1; design our own archetypes that test distinct skills. Never write that game's name in your
output.

Movement facts (shared controller): run speed 9 u/s, jump velocity 12 u/s, gravity 32 u/s^2 (max jump height
2.25 u, jump-cut supported), coyote 7 frames, jump buffer 6 frames, max fall 40 u/s, striker dash 28 u/s for 9 frames
(cooldown 45 frames), player box 0.8 x 1.8 x 0.8. Upgrades can add air jumps. Current platforms are axis-aligned boxes
(`Platform { id, kind, bounds: Aabb }`, kinds NORMAL / CRUMBLE); gifts and altars are points on platform tops; the
generator validates every hop against a jump envelope and a physics bot proves each level completable. Current
classes: striker (dash), grappler (auto-aimed grapple to a platform top ahead), blinker (6-unit teleport - to be
replaced), glider (+1 air jump, glide while holding ability and falling). Current enemy behaviours implemented in the
sim: chaser (flies at nearest target), turret (stationary, shoots bolts blocked by platforms), mimic (disguised as a
gift until close), corrupter (marks nearest platform to crumble). Enemies are voted in the lobby and stay for the run.

## Task
Write `design/M3_DESIGN.md`, a precise implementable design (numbers, not vibes) with these sections:
1. **Gifts and the two phases.** Gift count formula (about 50 on level 1, scaling with level and player count, capped
   for performance at 120), gift size and pickup radius, placement rules (on platform tops, spacing, a share on
   elevated/optional spots, none on crumble platforms), what triggers the second phase, the COLLAPSE (which platforms
   fall in which order - e.g. farthest from spawn first -, duration formula per level, warning time per tile), golden
   gifts appearing at every collected gift position, golden value, what happens to golden gifts on fallen tiles, the
   beacon (move it to the spawn hub, opens in phase 2), and how this changes shop prices (current prices assume ~5
   golden gifts per level worth 5 each - give the new value per golden gift and new price table for all 7 shop items).
2. **Enemy roster.** Rework ALL 9 existing enemies so each one tests ONE distinct skill and has a distinct movement
   and silhouette; keep their ids (pallbearer, snapshrike, moteling, rift_warden, gale_wight, lantern_leech, turret,
   mimic, corrupter) but you may rename and rewrite them. At least 2 must be non-lethal (debuff/displacement that sets
   up deaths). Every lethal attack has a telegraph of 0.6-2.5 s. For each enemy give: name, one-line fantasy, the
   demanded skill, a state machine (states, durations in seconds, transitions, targeting rule: nearest / random /
   behaviour-based), movement (speed u/s, through platforms or not), how it hurts (contact/projectile/area, radius),
   telegraph (what the client draws and for how long), counterplay, solo vs co-op notes, threat 1-5, and a short
   VISUAL brief (silhouette, materials, idle/attack animation; built from simple three.js primitives, glowing, readable
   in fog; distinct colour accent per enemy within the red-magenta danger family). Also: a global "heavy attack"
   mutex rule, and which data the server must send per enemy each tick for the client to draw telegraphs (be minimal:
   e.g. state, a target point, a 0-255 progress value).
   Constraint: all behaviours must be implementable server-side with deterministic logic over positions, platforms
   and player feet/velocity; the server does NOT know the player's camera direction.
3. **New class replacing the blinker.** Different verb from dash/grapple/glide (the human said blinker = striker but
   better). Specify ability rules frame-by-frame-ish (cooldown, durations, distances), what it is good at, and its
   one weakness. Must be implementable in the shared deterministic controller (state: pos, vel, grounded, counters,
   one Vec3 `ability_dir`, u8/u16 frame counters - you may propose ONE more small field).
4. **Modular maps.** A chunk system: define the chunk data format (JSON: platforms as boxes relative to the chunk
   origin, platform kinds incl. a new JUMP_PAD kind with its launch velocity, entry/exit sockets with position,
   facing and height, gift slots, enemy spawn slots, altar slots), connection rules (sockets must match facing;
   height changes between chunks; no overlaps; stacking = a chunk placed above another's footprint at >= 4 u
   clearance), minimum walkable width (3 u for paths, 6 u for hubs) and a hop envelope table (max horizontal gap for a
   given height delta for a plain jump, so designers stay inside it), and then the CATALOG: 25 named chunks each with
   a one-paragraph layout description and its rough size, elevation profile (e.g. "climbs 6 u via 3 steps"), sockets,
   difficulty 1-3 and minimum level. Must include: wide hubs, staircases up and down, a spiral tower, a stacked
   two-level bridge, jump-pad lifts, a long drop with a catch platform, branching junctions (2-3 exits), dead-end
   gift pockets, crumble bridges (min level), a few with optional high routes. Then the assembly algorithm (spawn hub
   first; random walk over sockets weighted by difficulty and level; branches; target total size by level; how to
   guarantee no overlap and completability).
5. **Escalation schedule.** Per-level milestones (which events/terrain/extra enemy copies unlock at which levels).
6. **Implementation slices.** Split the work into 5-7 tickets with disjoint files: protocol changes needed (fields
   and constants - list them precisely), sim controller (class + jump pads), sim hazards (enemies), sim levelgen
   (chunks), server run/game (gifts/collapse/beacon), client visuals, content/docs. For each: inputs, outputs,
   acceptance tests.
