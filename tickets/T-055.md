You wrote `sim::levelgen` (roads + hop envelope + physics bot). M3 replaces it with an assembler of hand-designed
chunks (design doc below; section 0 amendments are binding: MASSIVE maps, loops, stacked layers, rotations, gifts
lining the walkways, walkable 0.5 u stairs via controller step-up of 0.55 u). The catalog `design/chunks.json` is
being authored in parallel by another engineer in the exact format of CHUNK_FORMAT.md - write your code against the
spec, not against a particular catalog.

## Task
1. Rewrite `levelgen.rs` (you may split into `server/crates/sim/src/levelgen/*.rs` with `mod.rs`): parse the catalog
   from `include_str!` of `design/chunks.json` (path relative to the source file; from
   `server/crates/sim/src/levelgen.rs` it is `../../../../design/chunks.json`) once (a `std::sync::OnceLock`);
   expose `pub fn parse_catalog(json: &str) -> Result<Catalog, String>` so tests can use inline catalogs.
2. Assembly per design 4.3 + amendment A1: hub at origin (beacon at its `beacon` point; `LevelData.spawn` = a hub
   point >= 2.5 u from the beacon; `LevelData.beacon` = hub beacon), budget-driven random walk over open sockets with
   90 degree rotations, junction cap `4 + level`, min_level/difficulty weighting, overlap + 4 u stacking clearance
   checks (use a coarse grid for candidate tests - maps have hundreds of platforms), LOOP CLOSING with generated
   straight bridges (3-4 u wide) between facing open sockets within 12 u (|dy| <= 0.5), then dead-end sealing; any
   socket that still cannot be closed gets a short railing-less cap platform (a 3 u stub) so no walkway ends in an
   unexplained cliff. Platform ids are assigned in placement order starting at 0 = the hub's main platform.
   `kill_y = (lowest platform bottom) - 15`.
3. Gifts per amendment A3 (`generate(seed, level)` = 1 player; add `generate_for(seed, level, players)`): fill gift
   slots (elevated quota >= 20%), spacing >= 2.0 u, none on CRUMBLE/JUMP_PAD, none within 2.5 u of the beacon, at
   most one per 9 u^2 of eligible top; top up on random eligible tops if slots run short. All gifts GIFT_NORMAL
   (golden gifts appear at the same positions in phase 2 - the server handles that). Altars per the old rules
   (level >= 3, 50%) at altar slots. Enemy spawns = the hub's 8 enemy slots (transformed). Events: keep
   `event_for` (level 1 always none). EVENT_CRUMBLE turns ~40% of eligible path platforms (never hub, never with a
   gift slot) into CRUMBLE; EVENT_HIGH_RISE weights climbing chunks (tags "climb", "tower", "lift") x3.
4. `validate(level)`: structural checks + REACHABILITY over a platform graph (touching with step <= 0.55 u, jumps
   inside the design hop envelope edge-to-edge, jump pads up to +4 u within 5 u): every gift, altar and the beacon
   reachable from the spawn and the beacon reachable from everywhere reachable (no traps). On failure regenerate
   with the next seed (<= 40 attempts), then a guaranteed-valid fallback map built from the hub alone plus straight
   generated walkways in four directions.
5. Determinism: same (seed, level, players) -> identical LevelData (compare a hash in a test). Performance: a level-20
   map must generate + validate in < 150 ms in release builds (add an ignored timing test that prints the time).
6. Tests with small inline catalogs (hub + straight + stair + junction + dead end): socket joining and rotation
   math, overlap/stacking rejection, loop closing, sealing, gift rules, reachability failure detection, fallback.
   Plus one integration test over the real catalog (it will run once the catalog lands): 50 seeds x levels 1..10
   valid, platform-top area within +-15% of the budget on average, gift counts per A3.
7. `tests/playthrough.rs`: keep the physics bot but make it feasible for big maps: per (seed, level) the bot must
   reach 8 gifts chosen by the seed and then the beacon (instead of every gift); 10 seeds x levels 1..6. Keep the
   bot's hop logic; it may jump 0.5 u risers if step-up is not available yet (another ticket adds it).
