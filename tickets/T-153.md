# T-153 — `LobbyPoll` promised a feature that does not exist

**Cycle:** 23
**Status:** PASS
**Area:** `web/src/hud/LobbyPoll.tsx` (deleted), `web/src/hud/vote/__tests__/vote.test.ts`, `web/src/moduleWiring.test.ts`, `web/src/game/voteWiring.test.ts`

## The owner's decision

Cycle 22 parked `LobbyPoll.tsx` as an allowlisted orphan, with the note that deleting it was a
human decision. The owner's ruling:

> `LobbyPoll.tsx` — no permanent orphans. If the new physical lobby (T-120) uses pre-match
> polls, wire it in there. If the pedestal system supersedes it, delete the file and remove
> the allowlist entry. "Allowlisted orphan" is a state, not a home.

## What the investigation found

Neither branch of the decision applied as written, so the disposition needed a third answer.

**T-120 is not a physical lobby.** It is the ticket that made the dev code default to
`devaccess`. There is no physical-lobby ticket; the lobby is the spawn hub and `DraftScreen`
handles card picks there.

**`LobbyPoll` is not the pedestal vote.** It is a *pre-match theme/difficulty preference poll* —
a different mechanic from the pedestal vote that `RunVoteOverlay` now mounts. So the pedestal
system does not supersede it either.

**It is unimplemented, not superseded.** The component's copy claims theme and difficulty picks
"feed the pattern engine's tag weights". There is no `Poll` message in the protocol and no
server handler for one:

```
$ grep -rn "Poll" server/crates/protocol/src/generated.rs
$ grep -rn "Poll" server/crates/server/src/
```

Both return nothing. The component was written against a server feature that was never built,
so it could never have worked — mounting it would have shown players a poll whose answers went
nowhere.

## The fix

Deleted, because the honest state of the feature is "does not exist":

1. **`web/src/hud/LobbyPoll.tsx` deleted.**
2. **Its two tests removed** from `hud/vote/__tests__/vote.test.ts`, along with the import. The
   tests asserted the copy ("START POLL", "Skip the poll", `/pattern engine/`) — they pinned a
   promise, not a behaviour.
3. **The `TEST_ONLY` allowlist entry removed** from `moduleWiring.test.ts`. The allowlist's own
   second test fails on a stale entry, so this was required for green.
4. **The T-149 history comment in `voteWiring.test.ts` annotated** rather than rewritten: it
   still records that `LobbyPoll` existed and was unmounted, and now also records that T-153
   deleted it and why. Deleting the mention would have made the T-149 record wrong.

## What was deliberately not done

**No protocol message was added.** A pre-match theme/difficulty poll is a real feature idea, but
it is a feature, not a wiring fix: it needs a `Poll` message, a server handler, a vote tally,
and a consumer in the pattern engine's tag weights. That is a ticket of its own, and it would
have to go through `just gen` + `just fixtures`. It is logged as a candidate rather than
smuggled into a cleanup.

## Choices made

- **Deleted rather than mounted.** Mounting a poll with no server handler would put a dead
  control in front of players — the same class of defect as T-149, in the opposite direction.
- **The allowlist is now down to one entry** (`scene/enemyPalette.ts`, a measurement helper by
  design). The list is for things that are *meant* to have no importer, not for things waiting
  on a decision.
